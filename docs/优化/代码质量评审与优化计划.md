# AIGoat 代码质量评审与优化计划

> 评审范围：`src-tauri/`（Rust）、`web/src/`（TypeScript/React）、`tools/`（Python）
> 评审时间：2026-10-04
> 约束：不写入全局，仅落盘本项目 docs/优化/

## 1. 评审摘要

### 1.1 总体评价

AIGoat 的代码质量处于**良好偏上**水平，架构清晰、文档完备、约定明确。主要优势：

- **协议优先**：所有前后端交互以 `proto/scope.json` 为唯一真源，排除清单显式声明
- **分片合理**：Rust 映射层按事件类别分文件（threads/items/deltas/guard/host），前端 reducer 按条目类型分片（text/tools/turn/notice/question）
- **类型安全**：前端事件系统使用 discriminated union，拒绝 `[key: string]: unknown` 兜底
- **工具链完备**：`check_field_contract.py`、`check_wire_parity.py`、`scope_report.py` 三件套守住桥接层

## 2. 详细问题分析

### 2.1 超行数文件（🔴 高）

**问题描述**：00-总计划.md 已明确列出 10 个超 200 行文件。这是当前最大的可维护性瓶颈。

**根因分析**：
- `SettingsDialog.tsx`（850 行）：设置中心域化拆分已在 15 号文件规划，但尚未执行
- `shell.tsx`（406 行）：ShellState 接口 + slice 混在一个文件，职责边界模糊
- `reducer.ts`（383 行）：历史已拆成 `reducer/` 目录，但主入口仍保留大量旧代码
- `events.ts`（295 行）：事件类型定义 + 运行时分流混在一起
- 后端 `commands.rs`（754 行）：虽已按职责拆分子模块，但 mod.rs 中仍保留大量公共辅助函数

**优化建议**：
1. **立即执行**：按 00 号文件的分期路线图（A-G 期）逐一拆分
2. **设置拆分**：`SettingsDialog.tsx` → `SettingsDialog`（装配）+ `domains/`（各域独立）
3. **Store 拆分**：`shell.ts` → `shell/state.ts`（接口）+ `shell/connectionSlice.ts` + `shell/threadsSlice.ts` + `shell/turnsSlice.ts`（分片实现）
4. **Reducer 清理**：删除 `reducer.ts` 中已迁移到 `reducer/` 的旧代码，保留纯入口
5. **后端清理**：将 `commands/mod.rs` 中的公共辅助函数（`thread_summary`、`thread_full`、`status_payload`、`connect_info_json`）移到独立模块 `commands/helpers.rs`

### 2.2 事件消费缺口（🔴 高）

**问题描述**：部分协议事件到达前端后无处理或处理不正确。

**具体缺口**：
1. `item/tool/call` → 前端只插占位，永不应答
2. `client.review()` 已实现，但无任何调用点
3. `ImageView`、`ImageGeneration` 事件被静默丢弃
4. `hookPrompt`、`functionCallOutput` 被静默丢弃

**根因分析**：
- 事件映射层（`map/*.rs`）已正确转发，但前端 reducer（`reducer/`）缺少对应处理分支
- `item/tool/call` 的应答需要调用 `respondToolCall`，但前端没有对应的 UI 入口

**优化建议**：
1. **C 期优先**：补齐 `item/tool/call` 全链路应答（映射层已就绪，前端需补 reducer 分支 + UI 组件）
2. **C 期跟进**：为 `review()` 添加入口（可复用现有审批卡组件）
3. **B 期并行**：处理 `ImageView`、`ImageGeneration` 事件（映射层需补，前端需补渲染）
4. **静默丢弃审查**：建立 `unhandled` 事件白名单，避免真实新能力被淹没

### 2.3 桥接层字段名手写映射（🟡 中）

**问题描述**：Rust 映射层使用手写 `.get("X")` 读取协议字段，前端类型使用手写 interface 声明。两者之间无自动同步机制。

**根因分析**：
- 协议字段变更时，Rust 侧漏改会导致运行时 panic 或静默丢数据
- 前端类型漏改会导致编译错误（相对安全），但 `unknown` 类型的滥用会掩盖问题

**优化建议**：
1. **继续维护**：`check_field_contract.py` 已守住 Rust → 前端的字段名一致性
2. **增强**：添加 `check_wire_parity.py` 的反向检查（前端类型声明 ↔ Rust 映射输出）
3. **长期**：考虑使用 `ts-rs` 或类似工具自动生成类型定义，但需评估构建复杂度

### 2.4 前端测试覆盖不足（🟡 中）

**问题描述**：现有测试仅覆盖部分 reducer 和 slice，组件级测试几乎空白。

**根因分析**：
- 项目初期以功能落地为主，测试作为后续补充
- Zustand store 的纯函数性质适合测试，但组件交互测试缺失

**优化建议**：
1. **立即补充**：为 `reducer/` 中所有纯函数添加测试（text/tools/turn/notice/question）
2. **中期补充**：为关键交互流程添加组件测试（`threadOps.ts` 中的 guard 模式、approval 乐观定稿/回滚）
3. **长期目标**：核心用户流程（新建会话 → 发消息 → 工具调用 → 审批）端到端测试覆盖率 ≥ 80%

### 2.5 错误处理不一致（🟡 中）

**问题描述**：
- 部分 Tauri 命令在错误时返回 `Result<T, String>`，调用方需手动处理
- 部分命令在错误时返回默认值（如 `thread/list` 的空数组），静默吞错
- 前端部分操作显示 toast，部分仅更新 hint，部分无任何反馈

**根因分析**：
- 错误处理策略未在项目层面统一约定
- 不同板块由不同开发者实现，风格不统一

**优化建议**：
1. **制定约定**：
   - 网络/协议错误 → 显示 toast + hint
   - 用户操作错误（如删除运行中会话）→ 显示 toast + 阻止操作
   - 数据缺失（如空列表）→ 静默返回空，不显示错误
2. **前端统一**：创建 `useErrorHandler` hook，统一 toast 展示逻辑
3. **后端统一**：命令层错误分类（客户端错误 / 服务端错误 / 网络错误），返回结构化错误

### 2.6 魔法值与硬编码（🟢 低）

**问题描述**：代码中出现多处未提取的魔法值。

**示例**：
- `commands/threads.rs` 中 `DEFAULT_LIMIT: u64 = 50`
- `settings/ui_state.rs` 中 `500`（防抖毫秒数）
- `components/layout/columns.ts` 中 `SIDEBAR_DEFAULT` 等常量已提取，但仍有散落的像素值

**优化建议**：
1. **集中提取**：创建 `constants.ts`（前端）和 `constants.rs`（后端），统一管理魔法值
2. **命名规范**：常量名需体现语义（如 `DEBOUNCE_MS_UI_STATE_SAVE` 而非 `500`）

### 2.7 缺少 CI 可见（🟢 低）

**问题描述**：项目无可见的 CI/CD 配置，合并质量依赖人工审查。

**根因分析**：
- 项目初期以本地开发为主，CI 尚未搭建
- 00 号文件每期出口要求 `typecheck` + `build` + `clippy` + `verify.ps1` 全绿，但缺少自动化门禁

**优化建议**：
1. **立即搭建**：GitHub Actions 工作流，触发条件：PR + push to main
2. **必过检查**：
   - `npm --prefix web run typecheck`
   - `npm --prefix web run build`
   - `npm --prefix web run test`
   - `cargo clippy --workspace -- -D warnings`
   - `cargo build --workspace`
   - `python tools/check_field_contract.py`
   - `python tools/check_wire_parity.py`
3. **缓存优化**：缓存 `node_modules` 和 `target/`，将 CI 时间控制在 5 分钟内

### 2.8 高频事件路径锁竞争（🔴 高）

**问题描述**：Rust 后端事件处理路径上存在多处锁竞争，长会话高频事件下会成为吞吐瓶颈。

**具体表现**：
1. **`framing.rs:dispatch_frame`**：每个入站帧都加锁
   - `server_requests.lock().unwrap().remove(id)` —— 响应帧
   - `server_requests.lock().unwrap().insert(..)` —— 服务端请求
   - `active_turns.lock().unwrap().insert/remove` —— 回合边界
2. **`api.rs:request_with_timeout`**：每个出站请求都加锁 `self.pending.lock().unwrap().insert/remove`
3. **`commands/mod.rs:client()`**：每个 Tauri 命令都先拿 `state.client.lock()`
4. **`settings_cmds.rs`**：同一条命令路径中多次加锁读取 settings

**根因分析**：
- 事件流是最高频路径（每秒可达数十条 delta），锁粒度太粗
- `Mutex` 在 tokio 异步上下文中会阻塞整个任务线程

**优化建议**：
1. **短期**：将 `server_requests` 和 `active_turns` 改为 `DashMap`（无锁分段 map）
2. **短期**：`pending` 使用 `tokio::sync::RwLock` 或分段锁，读路径不加锁
3. **中期**：`AppState` 拆分细粒度状态（`SettingsState`、`ClientState`、`TerminalsState`），避免大锁
4. **监控**：添加事件处理延迟 histogram，定位热点

### 2.9 前端状态数组逐事件全量复制（🔴 高）

**问题描述**：前端 reducer 和 store 在每次事件处理时都创建新数组，高频事件下造成大量内存分配和 GC 压力。

**具体表现**：
1. **`reducer/*.ts`**：`push`、`replace` 都先 `state.entries.slice()` 再修改
2. **`store/ledger.ts:append`**：`const next = [...existing, row]` 每事件复制整条账本
3. **`store/snapshots.ts:rememberSnapshot`**：快照更新时复制整个 `TurnState`
4. **`grouping.ts:buildTurnBlocks`**：每次事件都重新分块、归组、建树

**根因分析**：
- Zustand 的不可变更新语义天然鼓励复制
- 消息流是最高频状态（每秒数十条 delta），但 entries 数组可能长达数千条

**优化建议**：
1. **短期**：`push`/`replace` 改用 structural sharing（如 `immer` 或手写 path-based update）
2. **短期**：`ledger.ts` 的 ring buffer 改用 `Array` 原地更新 + 版本号，只在超出 cap 时截断
3. **中期**：`entries` 改用 `Map<id, Entry>` + `order: id[]`，按 id 更新避免复制
4. **中期**：`useTurnBlocks` 增加浅比较缓存，entries 引用不变时跳过重组

### 2.10 子代理快照无上限淘汰（🟡 中）

**问题描述**：`snapshots.ts` 中 `MAX_SNAPSHOTS = 5` 只限制了非当前线程数量，但每个快照本身是完整的 `TurnState`（含 entries 数组），多子代理长会话会累积大量内存。

**根因分析**：
- 设计时假设子代理数量少、快照小
- 实际一个工具调用密集的子代理可以产生数千条 entries，5 个就是数万条

**优化建议**：
1. **短期**：快照也应用 ring buffer（如 `MAX_SNAPSHOT_ENTRIES = 2000`）
2. **中期**：子代理快照默认折叠为「摘要 + 最近 N 条」，展开时才加载全文

### 2.11 终端流与主事件流同通道（🟡 中）

**问题描述**：`turns.ts:ingest` 中 `terminalEvent` 通过 `useTerminals.getState().ingest(event)` 转交，但前端事件订阅是单通道——终端输出 delta 仍然经过 `recordToLedger` 和一源双投的分发。

**根因分析**：
- 账本需要记录终端事件（这是对的）
- 但 `terminalEvent` 的高频 delta 导致账本和消息流同步更新，触发了不必要的重渲染

**优化建议**：
1. **短期**：`terminalEvent` 在 `ledger.push` 中做采样（如每 100ms 合并一次），delta 不计入 `total`
2. **中期**：终端事件走独立的 Tauri event channel（`terminal-output`），与 `agent-event` 分离

### 2.12 滚动所有权查询 DOM 逐帧成本（🟡 中）

**问题描述**：`useScrollOwnership.ts:nearestEntryId` 在用户滚动时遍历 `[data-entry-id]` 元素并逐个调用 `getBoundingClientRect`，长消息流（数百条）下每帧成本高。

**根因分析**：
- `getBoundingClientRect` 触发同步布局（forced reflow）
- 滚动事件本身频率就高（60fps），与 DOM 查询叠加形成卡顿

**优化建议**：
1. **短期**：`nearestEntryId` 改为二分查找（条目 DOM 是按顺序的，用 `offsetTop` 数组缓存）
2. **短期**：滚动事件加 `requestAnimationFrame` 节流
3. **中期**：虚拟滚动（`@tanstack/react-virtual`），只渲染可视区域条目

### 2.13 前端无错误边界（🟢 低）

**问题描述**：`ConversationStream.tsx` 及下属组件没有 React Error Boundary，单条消息渲染异常会导致整条消息流白屏。

**根因分析**：
- 项目初期以功能为主，错误边界作为后续补充
- `TurnBlock` → `TurnRow` → `MessageItem` 层级深，任何一层抛异常都向上冒泡

**优化建议**：
1. **短期**：在 `ConversationStream` 和 `Ledger` 外层各包一个 Error Boundary
2. **中期**：`MessageItem` 增加 per-entry 错误降级（显示「该条目渲染失败」而非整条白屏）

### 2.14 配置加载静默降级（🟢 低）

**问题描述**：`settings/config.rs:load` 在读取失败时直接 `unwrap_or_default()`，坏配置被静默忽略，用户行为与预期不一致。

**根因分析**：
- 设计目标是「配置丢了不该挡住启动」
- 但坏配置（如手动编辑写错括号）和「没有配置文件」是两回事，后者才该静默

**优化建议**：
1. **短期**：区分「文件不存在」（静默默认）和「文件存在但解析失败」（提示用户）
2. **短期**：解析失败时备份坏文件为 `.json.bad`（已有）并展示 toast 提示

### 3.5 零拷贝优化（与性能并行）

> 背景：事件流是最高频路径，每秒数十条 delta。当前桥接层存在 **double allocation**
> （`json!` 建 Value 树 → Tauri IPC 再序列化），前端 reducer 存在 **per-event full-copy**
> （`entries.slice()` / `[...existing]`）。这些不是「可以优化」的地方，而是
> **长会话卡顿的根因**。

| 优先级 | 任务 | 预期成果 | 涉及文件 |
|--------|------|----------|----------|
| P0 | `deltas.rs` 闭包改为取 `&Value` 引用，消除每 delta 3 次 `Value::clone()` | 单 delta  allocations 减少 3 个 | `src-tauri/src/map/deltas.rs:11-13` |
| P0 | `framing.rs` 入站帧分发改为传 `&Value`，只在 HashMap insert 处 clone | 每帧减少 1 次 `params` 全量 clone | `src-tauri/src/codex/framing.rs:31-39,75-79` |
| P0 | `helpers.ts:replace/push` 改为 structural sharing（只复制修改 index 之后的部分） | 每 delta allocations 从 O(n) 降到 O(1) | `web/src/store/reducer/helpers.ts:32-43` |
| P1 | `item_kinds.rs` 字段访问改为 `unwrap_or(&Value::Null)`，让 `json!` 内部只 clone 一次 | 每 item event 减少 5-10 次 eager clone | `src-tauri/src/map/item_kinds.rs` 全文件 |
| P1 | `commands/mod.rs:thread_summary/full` 改用 derive `Serialize` 的结构体 | 每列表请求减少 250-500 次 field-by-field clone | `src-tauri/src/commands/mod.rs:65-100` |
| P1 | `ledger.ts:append` 用 Zustand functional updater 原地更新 `rows`，ring buffer 原地 append | 每事件减少 2 次大对象/数组 copy | `web/src/store/ledger.ts:103,128-129` |
| P2 | `snapshots.ts:rememberSnapshot` 用 `Map` + functional setter 替代 `{ ...snapshots }` shallow copy | 每快照更新减少 1 次 TurnState 全量 copy | `web/src/store/snapshots.ts:45-46` |
| P2 | 桥接层高频 delta 批量 emit（Rust read thread 累积 16ms 再发一条带数组的事件） | emit 频率从 100+/sec 降到 ~60/sec | `src-tauri/src/codex/framing.rs:140` |
| P2 | 评估 `Arc<str>` / `Arc<Value>` 在 bridge 层共享不可变事件对象 | 跨桥 allocations 减少 30-50% | 技术预研 |

### 3.6 零拷贝详细发现与修复方案

#### 3.6.1 Rust 侧：闭包 eager clone（Critical）

**文件**：`src-tauri/src/map/deltas.rs:11-13`

**现状**：三个闭包 `thread_id()` / `turn_id()` / `item_id()` 每次调用都执行
`.cloned().unwrap_or(Value::Null)`，而它们在每个 `json!({...})` 里都被内联调用一次。

**频率**：每个 `item/*/delta` 事件调用 3 次，每秒 50-200 个 delta。

**修复**：
```rust
// Before:
let item_id = || p.get("itemId").cloned().unwrap_or(Value::Null);
// After:
let item_id = p.get("itemId").unwrap_or(&Value::Null);
// json! 宏内部会对 &Value 做一次 clone，但只 clone 一次而不是每次调用都 clone
```

#### 3.6.2 Rust 侧：入站帧 params 全量 clone（Critical）

**文件**：`src-tauri/src/codex/framing.rs:31-39, 75-79`

**现状**：`dispatch_frame` 里 `frame.get("params").cloned()` 对每个入站帧复制整个 params 对象（可能包含大型 tool arguments）。

**频率**：每个 codex 通知/请求/响应都走这里，每秒 50-200 帧。

**修复**：
```rust
// Before:
handle_server_request(app, id.clone(), &method,
    frame.get("params").cloned().unwrap_or(Value::Null), ...);

// After:
handle_server_request(app, id, &method,
    frame.get("params").unwrap_or(&Value::Null), ...);
// 只在 HashMap insert 处 clone id（作为 key）
```

#### 3.6.3 Rust 侧：字段 eager clone 散落在 mapping 层（High）

**文件**：`src-tauri/src/map/item_kinds.rs` 全文件（至少 15 处）

**现状**：`item.get("name").cloned().unwrap_or(Value::Null)` 模式——即使字段存在，
也先 clone 再 unwrap，导致 eager allocation。

**频率**：每个 `item/started` / `item/completed` 事件。

**修复**：
```rust
// Before:
"name": item.get("name").cloned().unwrap_or(Value::Null),
// After:
"name": item.get("name").unwrap_or(&Value::Null).clone(),
// 或者如果 json! 宏支持 &Value：
"name": item.get("name").unwrap_or(&Value::Null),
```

#### 3.6.4 前端侧：entries 数组每事件全量复制（Critical）

**文件**：`web/src/store/reducer/helpers.ts:32-43`

**现状**：
```typescript
export function push(state: TurnState, entry: Entry): TurnState {
  return { ...state, entries: [...state.entries, entry] }
}
export function replace(state: TurnState, next: Entry): TurnState {
  const idx = state.entries.findIndex(e => e.id === next.id)
  return { ...state, entries: [...state.entries.slice(0, idx), next, ...state.entries.slice(idx + 1)] }
}
```

**频率**：每个事件都走 `push` 或 `replace`，每秒 50-200 次。`entries` 数组可能长达数千条。

**修复方案 A（短期）**：改用 `immer` 的 `produce`，内部做 structural sharing：
```typescript
import { produce } from 'immer'
export const push = (state: TurnState, entry: Entry): TurnState =>
  produce(state, draft => { draft.entries.push(entry) })
```

**修复方案 B（中期）**：entries 改成 `Map<id, Entry>` + `order: id[]`，按 id 更新避免复制：
```typescript
interface TurnState {
  entries: Map<string, Entry>      // 按 id 查找 O(1)，更新不复制
  order: string[]                   // 仅插入时复制尾部
}
```

#### 3.6.5 前端侧：ledger ring buffer 每事件双复制（Critical）

**文件**：`web/src/store/ledger.ts:103, 128-129`

**现状**：
```typescript
// pushHistory:
set({ rows: { ...get().rows, [key]: [...batch, ...existing].slice(-LEDGER_CAP) } })
// append:
set({ rows: { ...get().rows, [key]: [...existing, row] } })
```

**频率**：每个事件都调 `append`，每秒 50-200 次。`existing` 可能长达 5000 条。

**修复**：Zustand functional updater 原地更新，ring buffer 用 `Array` 原地 push + 版本号：
```typescript
set(state => {
  const next = state.rows[key] ?? []
  next.push(row)
  if (next.length > LEDGER_CAP) next.splice(0, next.length - LEDGER_CAP)
  return { rows: { ...state.rows, [key]: next } }
})
// 或者更好：ring buffer 类原地管理，外部只看到 getSnapshot()
```

#### 3.6.6 Rust 侧：桥接层 double serialization（Medium-High）

**文件**：`src-tauri/src/codex/framing.rs:140`

**现状**：每个事件经历 `Value → String (Tauri IPC) → Object (TS side)` 完整序列化/反序列化。

**频率**：每秒 50-200 次。

**修复方案 A（短期）**：Rust read thread 累积 16ms 的 deltas 再批量 emit：
```rust
// 在 read thread 里加一个 mpsc channel 做批量缓冲
let batch = BatchBuffer::new(Duration::from_millis(16));
for line in reader.lines() {
  let frame = parse(line);
  batch.push(frame);
  // 16ms 到点后一次性 emit 数组
}
app.emit(EVENT_CHANNEL, batch.into_array());
```

**修复方案 B（中期）**：TS 侧订阅 raw frames，自己做字段选择/重命名，消除 Rust 侧的 `map_notification`  allocations：
```typescript
// TS side:
client.subscribe(raw => {
  const event = mapEvent(raw)  // 纯 TS，零桥开销
  ingest(event)
})
```

#### 3.6.7 前端侧：snapshots shallow copy（Medium）

**文件**：`web/src/store/snapshots.ts:45-46`

**现状**：
```typescript
let nextSnapshots = { ...snapshots, [threadId]: turn }
let nextClock = { ...clock, [threadId]: now }
```

**频率**：每个触发快照的事件（ moderate）。

**修复**：用 `Map` + functional updater：
```typescript
const nextSnapshots = new Map(snapshots)
nextSnapshots.set(threadId, turn)
set({ snapshots: nextSnapshots, snapshotClock: new Map(clock).set(threadId, now) })
```

## 5. 风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 拆分超行数文件时引入回归 | 中 | 功能断裂 | 先补测试再拆分，CI 门禁保障 |
| 桥接层字段名变更时漏改 | 中 | 运行时错误 | 继续维护 `check_field_contract.py`，CI 必过 |
| 事件消费补齐时 UI 断裂 | 中 | 用户可见故障 | B 期先做 mock 事件回放，验证无视觉断裂后再接入真实事件 |
| 错误处理统一时行为变更 | 低 | 用户体验变化 | 分阶段迁移，旧行为保留 fallback |
| 锁竞争改造时引入死锁 | 中 | 后端崩溃 | 改造前写 `stress_test`（模拟 1000 并发事件），CI 必过 |
| 状态 structural sharing 引入 bug | 中 | 消息流渲染异常 | 先补 `reducer` 全量测试，再改实现 |
| 快照 ring buffer 丢失用户正在看的旧消息 | 中 | 用户困惑 | 只淘汰**非当前线程**的快照，当前线程快照不受上限约束 |
| 终端独立通道与账本采样冲突 | 低 | 账本时序不连续 | 采样用「最近一条 + 时间戳」，不丢事件只丢中间 delta |
| 虚拟滚动与折叠/嵌套树交互异常 | 中 | 消息流显示错位 | 先做消息流只读模式试点，验证 key 稳定后再全量 |
| structural sharing 引入引用不一致 | 中 | 消息流条目显示错乱 | 只改 `entries` 的存储结构，对外 API 保持 `Entry[]` 不变 |
| `immer` 引入不可变更新 bug | 中 | 状态更新不符合预期 | 先补 `reducer` 全量快照测试，再接入 `immer` |
| Rust 传 `&Value` 生命周期早于 emit | 低 | 悬垂引用 panic | `json!` 会在 macro 内 clone，确保 emit 前不释放引用 |
| 批量 emit 导致事件延迟增加 | 低 | 用户感知到输出变慢 | 16ms 批量窗口是可接受的（低于一帧），tool delta 单独处理 |
