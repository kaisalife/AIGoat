# 16 · 状态管理与数据流

> 抄 dsh：分层单向流＋投影注册表（`packages/client/store/src/contract.ts`、`api/session-controller/client`、docs/subsystems/web-client.md）｜协议：现有 agent-event 流｜决策：**改**（zustand 保留，抄「一源双投＋投影」思想）

## 1. dsh 的架构（值得抄的部分）

```
Host 服务 → 传输 → React-free Client 模型（Session 持事件窗口/游标/翻页）
              → UI 适配 hooks（useSession 等）
              → Conversation 装配器（事件/视图双注册表：同一事件流独立投影出 Chat 与 Trajectory）
              → Slots → React
```

- store 引擎：ObservableSnapshot + immer actions + persist；
  `useSyncExternalStore` 只在渲染层绑定。
- **投影（projection）注册表**：sessionStats / turnOutline / contextPressure /
  contextBreakdown——派生数据按注册表计算，组件按名消费。
- 重连语义：物理层与逻辑层分离，逻辑层基线原子替换。

## 2. AIGoat 现状与差距

- zustand 分域已有（shell/workspaces/resources/reducer/entries/editor/ui），
  但：shell.ts 406 行大杂烩；reducer.ts 383 行；右栏数据手动 load 非事件驱动；
  无投影层；无"同一事件流多视图"的消费结构（Trajectory 需要原始流，
  reducer 只输出 Chat 视图）。

## 3. AIGoat 改造设计

### 3.1 目标数据流（一源双投）

```
agent-event（tauri.ts subscribe）
  ├──► EventLedger（06：原始账本 ring buffer，含 Unhandled）──► Trajectory 视图
  └──► reducer（AgentEvent → TurnState/Entry 快照）──────────► Chat 视图
组件 ──► store.action ──► BridgeClient ──► bridge_* ──► codex
```

### 3.2 store 目录重组（行数目标）

```
store/
├── index.ts          装配导出（≤60）
├── shell.ts          连接态/当前线程/回合控制（从 406 瘦身，≤200）
├── threads.ts        会话列表态＋CRUD（03）（≤200）
├── turns.ts          回合态＋pending 回显（04）（≤200）
├── ledger.ts         事件账本（06）（≤200）
├── resources.ts      右栏资源态：改事件驱动订阅（10）（≤200）
├── workspaces.ts     不变（139 ✅）
├── editor.ts         不变（170 ✅）
├── ui.ts             +MainView/detailLevel/dock 态（01/04）（≤150）
├── settings-ui.ts    useSettingsStore（15）（≤140）
├── reducer/
│   ├── text.ts       文本/推理事件（≤200）
│   ├── tools.ts      工具/文件/命令事件（≤200）
│   └── turn.ts       回合生命周期/压缩/审核（≤200）
├── projections.ts    投影注册表：turnOutline/contextPressure/sessionStats（≤200）
└── entries.ts        Entry 模型 +12 种（≤200）
```

### 3.3 投影注册表（抄 dsh 概念，zustand 实现）

```ts
// projections.ts：派生数据注册表，组件 useProjection(name, threadId) 消费
type Projection = (snapshot: StoreSnapshot) => Derived
registry: {
  turnOutline:      回合大纲（TurnRail 数据源，04）
  contextPressure:  上下文占用（ContextMeter 数据源，13）
  sessionStats:     会话统计（回合数/工具数/token 累计，StatusBar/Trajectory）
}
```

- 实现：reducer 输出快照后按需重算（zustand subscribe + selector 缓存，
  不引 immer/新库——派生用纯函数 + memo）。
- 投影是**唯一**的派生数据出口：组件禁止自行 reduce store（写在
  AGENTS 约定里）。

### 3.4 事件驱动右栏（去手动 load）

C 期事件映射补齐后：`mcpServer/startupStatus/updated`、`skills/changed`、
`hook/{started,completed}`、`windowsSandbox/setupCompleted` 等直接驱动
resources 态；`resources.load()` 降级为手动刷新按钮（保留兜底）。

### 3.5 重连语义

物理层（Tauri event 通道）与逻辑层（线程快照）分离：断线时快照保留，
重连后 `thread/list` + 当前线程 `thread/items/list` 做基线原子替换
（与 04 本地回显、06 账本续写协同——账本以基线替换为界去重）。

- [x] ledger 一源双投接线（`slices/connection.ts` 的 subscribe：先 `recordToLedger` 再 `ingest`）
- [x] shell/threads/turns 三分拆（`store/shell.ts` + `store/slices/{connection,threads,turns}.ts`）

- [x] projections.ts 三投影 + useProjection hook —— `store/projections.ts`：
      `turnSummaries`（回合摘要，间隔用 `startedAt` 差而非"跑了多久"——用户
      关心的是等待体感）、`sessionStats`（跨回合累计）、`budgetPressure`
      （上下文余量，两档阈值）+ `useProjection` 与三个便捷 hook。
      `budgetPressure` 的 `used` 用 `input + output`：**缓存命中的部分
      仍然占窗口**（它要被读一遍），不算它进"省下来的额度"
- [x] resources 事件驱动改造 —— `REFRESH_PLAN` 表把
      `mcpProgress` / `skillsChanged` / `projectChanged` /
      `sandboxSetupCompleted` / `worldWritableWarning` / `authRecovery`
      映射到对应刷新，带**同类并发去重**（一次 MCP 变更连着来好几条，
      逐条刷会把右栏闪成筛子）。`output`/`fsChanged` 这类高频流**不列**——
      它们不改变右栏任何一块的内容，刷了纯浪费
- [x] 重连基线替换（thread/items/list 依赖 17 期）—— `store/baseline.ts`
      整段**替换**而非追加（追加会把两边都收到的条目算两遍），按 `turnId`
      重建回合边界，顺带清掉账本（它里面"重连期间收到"的行会和基线重复）。
      入口：状态栏的「连接已断 · 重新连接」→ `shell.reconnect()`
- [x] 纯函数单测（vitest）—— `summaries` / `baseline` / `projections` /
      `threadOrder` / `approvalPolicy` 共 81 例，已接进 `verify.ps1` 的第七道关。
      **测试抓到一个真 bug**：`projections.ts` 用真值判断
      `meta.endedAt && meta.startedAt`，而 `baselineFromItems` 的时间戳缺省时
      按序号占位、**首项就是 0** ——于是重连基线重建出来的首个回合时长被静默丢掉。
      已改成 `!= null`。这就是纯函数该有单测的理由：它不崩，只是安静地显示错的数字

## 4. 审查补记（2026-10-04 全量核对后）

### 4.1 三项的实现记录

**① `projections.ts`（本轮补）**
散着算的风险不是现在算错，而是同一口径被算两次之后慢慢分叉——比如状态栏算
「本轮」而回合头算「累计」。`useProjection` 的 `useMemo` 不是可选的：
`turns` 在流式期间每帧都变，没有这层 memo 时，状态栏一个 2000ms 的间隔
计算能让整棵消息流跟着每帧重算。

**② resources 事件驱动（本轮补）**
真源在 C 期就通了，缺的只是一个消费者。防抖那 800ms 是量出来的：一次
`mcpServer/*` 变更往往连着来好几条（startupStatus + 若干 event/stream）。

**③ 重连基线替换（本轮补）**
后果要分两半看：断线重连**不会崩**也不丢当前会话，但在补基线之前
**账本不连续**——重连期间的事件再也收不到了，而账本连续性正是 06 号板块的
核心验收项之一。所以这一项不是"锦上添花"，是补一个会**说谎**的界面。
