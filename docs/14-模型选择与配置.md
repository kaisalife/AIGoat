# 14 · 模型选择与配置（独有功能融合）

> 抄 dsh：`packages/client/ui-model-selection/`（/model popup：fuzzy＋分组＋composer seat）｜协议：**不用** `model/list`（AIGoat 立场：自定义目录是唯一真源）｜决策：**改**（交互抄 dsh，数据源是本地 settings）

## 1. dsh 的设计

- `/model` 命令唤起 popup：fuzzy 搜索 + 按供应商分组 sticky 标题；
  composer 上有当前模型 seat（常显当前模型名，点击即开 popup）。
- Models 设置页：API key 管理、模型列表、自定义路由。

## 2. AIGoat 立场（不可动摇的既有决策）

**codex 内置模型目录一概不用、不显示**（README 既定）：
启动子进程用 `-c` 覆盖项钉死 `model_provider`/`model`，强制
`requires_openai_auth=false`＋`wire_api="responses"`，无回落内置端点路径。
因此：

- `model/list` 协议方法**不接**（避免两个真源打架）；
- /model popup 的数据源 = `bridge_settings_get` 的自定义模型目录；
- dsh 的"供应商账号分组"（deepseek-account 等）不抄（云端账号排除，18）。

### 4.1 为什么 rerouted 徽标要查账本

`guardEvent` 在 C 期已经映射，并且已经进了事件账本（06）。徽标直接从账本
查当前会话最近的 `modelRerouted`，**不再 `client.subscribe` 一次**。

理由和终端那处一样：一条事件两个消费者会让「是谁改的状态」变得难追；
而账本本来就是"发生过什么"的忠实记录——它是唯一已经持有这条事件的
地方。

限定 `turnId`：改派是**逐回合**的行为，把上一轮的改派一直挂着会让人
以为当前还在用被换掉的模型。

### 4.2 `approvalPolicy` 与档位 id 的鸿沟（跨板块）

`/permission` 想"选中即应用"时撞上一堵墙：协议的 `approvalPolicy` 是
`untrusted` / `on-request` / `never` / granular 对象，而
`permissionProfile/list` 返回的是**档位 id**（见 docs/17 §5.5 的核实记录）。
两者不是同一套词汇，需要一张映射表。

而这张表该由谁维护还没定：协议侧加档位时是否同步加 `approvalPolicy` 的
取值，manifest 里看不出来。所以在映射表落地之前，`/permission` 选中档位
**只落设置**（新会话默认），不谎称已对当前回合生效。
