### 4.1 三个实现期的关键决定

**① 草稿轨存的是路径，不是 File。**
协议的 `UserInput` 有 `localImage: { type, path }` 这一项（docs/17 §5.8），
图片**不需要**先 `thread/attachment/add`、也不需要转 base64。
所以拖放必须走 Tauri 的 `onDragDropEvent`——它给真实文件系统路径，
而 HTML5 的 DataTransfer 只给 `File` 对象、**拿不到路径**。为了绕开
这一点而多背一份图片进内存，是本末倒置。

**② `UserInput.text_elements` 是 snake_case，我们原来写错了。**
协议的 text 变体里那个字段就叫 `text_elements`（生成产物确认），
其余字段（`isOther` 等）才是 camelCase。写成 `textElements` 的话 codex
会当成未知字段**静默忽略**——不报错，表现为"标注功能莫名其妙不生效"。
已修正并在该类型上写了注释钉住这一点。

**③ 交付物卡从条目聚合，不用 `turn/diff/updated`。**
后者给的是整轮合并的 diff 文本、**没有文件路径**，做不了"点击文件跳转"。
`fileChange` 条目天然按文件分组（05 号板块已映射），从那里聚合才能拿到
每文件独立的 diff，代价只是自己数 `+`/`-` 行。

### 4.2 裁决出口已核实，但按钮刻意禁用

docs/17 §5.7 核实结论：**出口是 `thread/approveGuardianDeniedAction`**，
参数 `{ threadId, event }`，而 `event` 是序列化的
`GuardianAssessmentEvent`——也就是 `strictReviewRequired` 通知里那份评估
对象。所以「驳回理由」不是一段文本，而是**把那次评估事件原样回灌**；
响应是空对象。

那为什么不接？因为**接错了的代价是不可逆的**：点了"驳回"却把代码真改
下去了，或者点了"批准"却永久放行了一批不该自动跑的改动。所以队列这一期
只读，`全部批准 / 全部驳回` 置灰并把出口名写在界面上——让读代码的人
一眼知道下一步要接什么，而不是让用户点一个不知道会做什么的按钮。

### 4.3 附件上限的取舍

20MB 是 11 号文件定的。超限时**拒收并说明原因**（"23.4MB 超过 20MB 上限"），
不静默丢弃——用户拖了个大图发现什么都没发生，会以为功能坏了。
读不出预览（`fs_read` 失败）时显示占位图而**不是拒收**：协议要的是路径，
codex 那边读得到就行，浏览器读不到只是界面上少张缩略图。
