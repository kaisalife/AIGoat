# 13 · 上下文计量与压缩

> 抄 dsh：`ui-conversation/src/client/skeleton/ContextMeter.tsx`（环形占用率＋breakdown）＋`ui-chat/src/client/chat/CompactionCommandCard.tsx`｜协议：`thread/tokenUsage/updated`＋`contextCompaction`＋`compact/start`｜决策：**抄**

## 1. dsh 的设计

- **环形占用率**：composer 下方的环形（ring）进度——上下文用了多少，
  一眼可读；点击展开 token breakdown 面板。
- **breakdown 面板**：system / tools / messages 三段分布，解释"上下文被
  什么吃掉了"。
- **压缩卡**：`/compact` 触发的压缩过程在消息流里是独立命令卡（进行中 →
  完成态），完成后**显式提示历史已被摘要**（用户必须知道）。

## 2. codex 协议支持

| 需求 | 协议 | 状态 |
|---|---|---|
| 用量事件 | `thread/tokenUsage/updated` | ✅ 已映射（现有 tokenUsage 余量条的数据源） |
| 压缩事件 | `thread/compacted`＋`contextCompaction` Item | ✅ 已接（显式提示条已有） |
| 压缩触发 | `thread/compact/start` | ✅ 已接（/compact 命令 08） |
| 分段 breakdown | **无 system/tools/messages 三段数据**——tokenUsage 形态以 manifest 为准（通常是 lastTokenUsage: input/output/cached + limit） | ⚠️ 降级 |

**数据源约束（设计红线）**：不虚构 breakdown。codex 的 tokenUsage 不提供
dsh 那种三段分布——本板块抄的是**环形 + 可展开**的交互骨架，展开面板内容
降级为：总量（input/output/cached/limit 四值 + 缓存命中率），标注
"受协议数据所限"。若未来上游补分段字段再启用。

上下文错乱。

### 4.1 实现期确定的三件事

1. **环形放在输入框的下缘，不放消息流顶部**。上下文占用恰恰是**发消息之前**
   最该看到的信息，而消息流顶部会随滚动跑出视野。
2. **`cached` 单列并给命中率**。它是 `input` 的子集，混在 input 里会让人
   以为每轮都要全额计费。命中率高恰恰是这套自定义 provider 配置生效的信号。
3. **`limit === 0` 时不画环，显示问号**。模型目录里没填上下文窗口是常态，
   画一个「100% 满」的环会让人以为上下文用尽了——这比不显示更糟。

### 4.2 数据源约束的落地

`contextPressure` 没有单独立投影（16 号板块的 store 改造还没做），这一期直接
在 `Composer` 里用 `shell.tokens` 与 `shell.contextWindow` 算：

```
used  = input + output
ratio = used / contextWindow
```

理由是**这两个值已经是快照**，再包一层投影只是换个地方存同样的数。
等 16 期真的动 store 结构时再把它挪进去——那时它才有独立的订阅价值
（多个消费方各自订阅，避免一起重渲染）。
