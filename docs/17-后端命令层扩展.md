## 5. 协议核实点（C 期已逐项过 `codex app-server generate-ts`，2026-10）

结论以 `codex app-server generate-ts` 产物为准，下方类型名即产物里的文件名。

### 5.1 attachment add 载荷

`ThreadAttachmentAddParams = { threadId, attachmentType, identityKey, payload }`

- **不是路径、不是 base64**：`payload` 是 `JsonValue`，由 `attachmentType`
  决定形状。宿主只透传，不解析。
- `identityKey` 是幂等键：同 key 重复 add 是"取或建"而不是重复创建。
- 推论：**不预读文件、不校验大小**，那是 codex 侧的事；宿主硬加校验
  会在协议升级时变成阻塞点。

### 5.2 requestUserInput 的 params schema

`ToolRequestUserInputParams = { threadId, turnId, itemId, questions, isBlocking, autoResolutionMs }`

- `questions: ToolRequestUserInputQuestion[]`，每题
  `{ id, header, question, isOther, isSecret, options: ToolRequestUserInputOption[] | null }`
- **`options === null` 是纯填空题**，有值才是选择题——两种形态必须分别渲染。
- `autoResolutionMs` 字段带 `@deprecated`，**判断阻塞要看 `isBlocking`**。
  按 deprecated 字段实现会在上游清理后静默失效。
- 应答形状：`ToolRequestUserInputResponse = { answers: { [questionId]?: answer } }`
  —— **与审批的 `{decision}` 完全不同**，混用会被当非法应答丢掉。

### 5.3 goal 的 paused 字段

`ThreadGoalStatus = "active" | "paused" | "blocked" | "usageLimited" | "budgetLimited" | "complete"`

- **没有 `paused` 布尔字段**，`paused` 是 status 的一个枚举值。
  07 的暂停按钮要写 `set { status: "paused" }`，不是 `set { paused: true }`。
- `ThreadGoalSetParams` 的三个字段（`objective`/`status`/`tokenBudget`）
  都是可选且可为 null——**null 语义是"不动它"**，不是"清空"。

### 5.4 review 裁决出口

`ReviewStartParams = { threadId, target, delivery }`

- `delivery: "inline"`（默认，当前线程内跑）或 `"detached"`（新线程，
  返回 `reviewThreadId`）。
- **`detached` 已 deprecated** 且会发 `deprecationNotice`。独立复核线程应走
  `thread/start` + inline review，不要用 detached。
- 裁决出口仍是**给复核线程发消息**（`turn/start`），不是另一个专门的
  approve 方法——`bridge_review_start` 只需起线程，后续走正常发消息。

### 5.5 approvalPolicy 在 turn/start 的参数位置

`TurnStartParams.approvalPolicy?: AskForApproval | null`

- 位置确认：顶层字段，与 `sandboxPolicy` / `approvalsReviewer` / `effort` 并列。
- `AskForApproval = "untrusted" | "on-request" | "never" | { granular: {...} }`
- **与 `permissionProfile/list` 返回的 id 不是同一套词汇**：前者是
  `untrusted/on-request/never` 字符串或 granular 对象，后者是档位 id。
  所以"设置里选档位 → 应用"需要一张映射表，不能直接把 id 塞进
  `approvalPolicy`。

### 5.6 terminal exec 的 id 语义与 resize 时序

`CommandExecParams` 的关键约束（文档字符串明确写了）：

- **`processId` 缺省时服务端用内部 id，且这个 id 不暴露给客户端。**
  所以 `tty` / `streamStdin` / `streamStdoutStderr` / 后续的
  `write|resize|terminate` **全部要求客户端自带 `processId`**。
- `command/exec` 的应答**推迟到进程退出**才发，且在所有 outputDelta 之后。
  所以命令层不能同步等它——必须"先回 pending 标识，输出全走事件"（§2 的
  同一条约束再次得到印证）。
- `outputBytesCap` 与 `disableOutputCap` 互斥；`timeoutMs` 与
  `disableTimeout` 互斥。两个都不传就走服务端默认。

### 5.7 Review 裁决的协议出口（G 期核实）

**裁决出口是 `thread/approveGuardianDeniedAction`**，参数与响应：

```
ThreadApproveGuardianDeniedActionParams  = { threadId, event: JsonValue }
ThreadApproveGuardianDeniedActionResponse = Record<string, never>
```

- `event` 是序列化的 `GuardianAssessmentEvent`——也就是
  `autoApprovalReview/strictReviewRequired` 通知里那份评估对象。
  所以「驳回理由」不是一段文本，而是**把那次评估事件原样回灌**。
- 响应是空对象：调完即定稿，没有别的东西要读。
- 11 号文件 §4.2 那个"裁决出口未核实"的阻塞到此解除，但 Review 队列的
  UI 本期仍未做——它要先能拿到 `strictReviewRequired` 的完整载荷并渲染，
  而右栏的 review 队列位置属 10 号板块之后的工作。

### 5.8 `UserInput` 的本地图片（11 号文件 §3.1 的核实点）

```
UserInput = { type:"text", text, text_elements }
          | { type:"image", detail?, url | fileId }
          | { type:"localImage", detail?, path }     ← 关键
          | { type:"audio", url } | { type:"localAudio", path }
          | { type:"skill", name, path } | { type:"mention", name, path }
```

- **`localImage` 带本地路径**，所以图片可以直接进 `turn/start` 的 `input`，
  不必先 `thread/attachment/add`。草稿轨因此只需存**本地 File 列表**，
  发送时整包进 input——这正是 11 号文件 §4.1 那张表的第二行。
- `turn/start` 同时接受 `approvalPolicy` / `sandboxPolicy` / `model` /
  `effort` 的**逐回合覆盖**，也就是说档位/沙箱其实不必走 `thread/start`
  就能按回合切换（§5.5 的映射表问题因此只影响"新会话默认"这一层）。

### 5.9 `turn/start.clientUserMessageId`

`TurnStartParams` 有 `clientUserMessageId?: string | null`。

- 协议**接受**它，所以前端回显 id 应当原样带上去——这是本地回显
  （04 §3.2）能精确认领的前提。
- 但生成的类型里 `UserMessage` item 上**没有**这个字段，所以服务端
  不一定回传。前端因此保留正文匹配作兜底（`localEcho.claimEcho`）。

### 7.1 宿主 fs 工具与"fs/* 明确不接"的关系

§2 说 `fs/*` 9 项方法明确不接，理由是"本地 `bridge_fs_*` 已工作，双通道徒增
风险"。C 期又提供了宿主侧的 `fs_*` 客户端工具——**这两件事不矛盾**：

| | 方向 | 触发方 |
|---|---|---|
| `fs/*` 方法 | 客户端 → codex | codex 让宿主用它的文件系统 |
| `item/tool/call` + 宿主工具 | codex → 客户端 | codex 让**宿主**替它做 |

宿主工具走的是完全独立的通道（server 请求 + 应答），不经过 `fs/*`。
但既然两者做同一件事，就把边界写死：

- **只提供只读**。写盘必须走审批流程（12 期），不能从这条旁路绕过——
  那等于开了一个免审批的写盘口子。
- **只注册到 `clientTools.ts` 这一个注册表**，不新增 bridge 命令；
  复用已有的 `bridge_fs_*`，不重写一遍文件访问。
- 未注册的工具一律回 `success: false` + 明确错误，**绝不装死**。

### 7.3 为什么 `approvalPolicy` 那一半没做

`/permission` 命令注册了，选中档位**只落设置**（新会话默认），不对当前回合
声称生效。原因是 §5.5 核实出的那堵墙：

| | 词汇 |
|---|---|
| `permissionProfile/list` 返回 | 档位 id（`read-only` 之类） |
| `turn/start.approvalPolicy` 要 | `untrusted` / `on-request` / `never` / granular 对象 |

两者不是一套词，中间需要一张映射表，而**这张表该由谁维护还没定**
（协议侧加档位时是否同步加 `approvalPolicy` 取值，manifest 里看不出来）。

在归属明确之前把 id 直接塞进 `approvalPolicy`，表现会是"设了但没用"——
比不设更难排查。所以宁可不声称生效。

（另外三处按设计未做／待接：Review 裁决按钮等出口接入、Timeline 的缩放平移、
`/skill` 的二级选择、`/export` 的全量导出。理由分别写在 11/06/08 号文件里。）

### 7.4 事件通道的第三种结局

原来的设计只有"映射"与"未建模"两种。本期加了第三种：**已知但不消费**
（`map/mod.rs` 的 `DECLINED` 表）。

| 结局 | Rust 侧 | 前端表现 |
|---|---|---|
| 已建模 | 产出事件 | 正常渲染 |
| 见过且刻意不做 | `Some(Value::Null)` | 静默丢弃 |
| 真没见过 | `None` | 落 `unhandled`，界面一行灰字 |

不把这三种分开的话，账号体系、`thread/realtime/*` 这些"看过但不做"的通知
会和"上游升级了"混在一起，真正的新能力被淹没。`DECLINED` 每条都带决策
依据，将来要接回来删一行即可。

验收：`cargo clippy --workspace -- -D warnings` 干净、`cargo test` 全绿、
`tools/verify.ps1` 全绿；每文件 ≤200 行；新增命令均有前端调用点
（不做无消费的命令）。
